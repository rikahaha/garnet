# 成本核实：存活内存与字典＋排序树

2026-10-30，本机 Darwin arm64，.NET SDK 10.0.403，Release。
本轮只修改 member_protocol；没有接入 Garnet、连接服务器、提交或推送。

## 方法与复现

新增 `CostStudy.cs`、`run_cost_study.py`。两种规模（10K、100K）、两种成员长度
（16、128 字节），每组 3 个独立进程。共 108 条正式测量记录。
每个进程只运行一个配置，输入成员互异且固定。未引入第三方包。

```sh
/usr/local/share/dotnet/dotnet build research/checkpoint_cou/member_protocol/MemberProtocol.csproj --no-restore -c Release -m:1 -p:UseSharedCompilation=false -nodeReuse:false
python3 research/checkpoint_cou/member_protocol/run_cost_study.py /usr/local/share/dotnet/dotnet cost_study_serial.jsonl
```

驱动拒绝覆盖已有文件；重跑需换输出文件名。正式数据：`results/cost_study_serial.jsonl`。
`cost_study.jsonl` 是早期诊断轮，部分时间与回归测试重叠，不用于本文延迟结论。
`cost_regression.txt` 记录修改后的原有两组测试和 2000 轮并发测试，全部 PASS。
正式轮开始前已等待回归进程和诊断测量退出；未主动运行其他负载，但没有隔离操作系统噪声。

## 1. 存活内存

输入数组先创建并用静态字段保活，不计入容器增量；测量容器的额外存活空间。
用显式静态 root 保活被测对象，暖身后完整阻塞压缩 GC 两次，读取
`GC.GetGCMemoryInfo().HeapSizeBytes - FragmentedBytes` 的前后差值。
另记录线程初始化分配量和进程 PeakWorkingSet64。后者包含 CLR、JIT 和输入数组，
不能把进程 RSS 差直接归因于节点。此方法改善了之前 GC.GetTotalMemory 差值不一致的问题，
但仍是受控堆差分，不是 heap dump 的逐对象归因或严格硬内存预算。

以下为 100K 成员的 3 轮中位数，MiB = 2^20 字节：

| 结构 | 16 字节成员 | 128 字节成员 |
| --- | --- | --- |
| 仅字典，共享已有成员数组 | 4.18 MiB | 4.18 MiB |
| Owner，共享已有成员数组 | 11.04 MiB | 11.04 MiB |
| Owner，复制成员数组 | 14.86 MiB | 25.54 MiB |
| 字典＋排序树，共享成员数组 | 9.52 MiB | 9.52 MiB |
| Owner＋排序树，共享成员数组 | 16.38 MiB | 16.38 MiB |

共享 Owner 相对字典约多 **72.00 字节/成员**；配合排序树时约多 72.00 字节/成员。
10K 组得出相同增量，但字典容量舍入使每成员容器成本不同。
单独构建节点引用数组测得约 80 字节/成员，其中约 8 字节是该测试数组的节点引用，
与节点增量约 72 字节相符。节点旧分数字段平时已分配，首次保护不再分配旧值对象。

复制数组额外约为：16 字节 payload 对应 **40 字节/成员**，128 字节 payload 对应
**152 字节/成员**，包括数组头和对齐。两种长度均比裸 payload 多约 24 字节。
这说明复用已有不可变成员数组值得争取，但不能在 Garnet 接入前假设所有路径都满足该契约。
本轮为 Owner 增加默认关闭的 `borrowKeys`，仅供这些受控基准共享预先创建且从不修改的数组；
默认仍复制，不改变原型的输入所有权安全契约。

100K、128 字节、共享数组的 Owner：开始快照约增加 48 字节；删除一半未扫描成员后，
旧节点仍保留；Close 后约释放 3.6 MB 节点。复制数组版本 Close 后另释放约 7.6 MB 成员数组。
共享输入数组仍被测试 root 保活，因此不会随节点回收。字典容量不会缩小。
GC 差值还存在少量运行时噪声，不把几十字节或几 KB 差异解释为精确结构尺寸。

## 2. 字典＋排序树延迟

两组使用同一 byte[] 内容比较器、score/成员字节排序规则、共享不可变输入数组和外层 monitor。
每次 Set 删除旧排序项、更新字典/Owner，再插入新排序项；检查删除、插入结果。
每进程先暖身 20K 次，再记录 100K 次更新的逐操作 Stopwatch 延迟。
遍历成员采用固定互质步长，覆盖全部成员，无网络、编码或输出。

Owner 组用自己的字典取代基线分数字典，不再额外维护一份成员字典；
但当前适配器会在外层树锁内两次获取 Owner gate（查询旧分数、Set），且保留 Owner 计时。
所以这仍是独立原型适配器成本，不能当成最终 Garnet 接入实现的精确增量。

“扫描”组有一个后台线程不断 Begin、以 128 节点/16 KiB 分批读取并 Close，期间前台更新；
批次之间 Yield。它刻意造成持续扫描竞争，不代表实际 checkpoint 频率。
基线组没有全量序列化或后台扫描，不能用此对比声称 checkpoint 性能提升。

表内为 3 次运行各自统计值的中位数，单位 μs（不是合并样本的分位数）：

| 成员数 / 字节 | 配置 | p50 | p99 | p99.9 |
| --- | --- | --- | --- | --- |
| 10K / 16 | 字典＋树 | 1.083 | 1.583 | 4.958 |
| 10K / 16 | Owner＋树 | 1.125 | 1.667 | 5.041 |
| 10K / 16 | Owner＋树＋扫描 | 1.375 | 5.541 | 13.625 |
| 10K / 128 | 字典＋树 | 1.166 | 1.792 | 8.666 |
| 10K / 128 | Owner＋树 | 1.167 | 1.750 | 5.083 |
| 10K / 128 | Owner＋树＋扫描 | 1.458 | 5.500 | 12.084 |
| 100K / 16 | 字典＋树 | 1.916 | 3.250 | 9.916 |
| 100K / 16 | Owner＋树 | 1.959 | 3.375 | 10.000 |
| 100K / 16 | Owner＋树＋扫描 | 2.541 | 6.958 | 123.542 |
| 100K / 128 | 字典＋树 | 2.042 | 3.666 | 7.042 |
| 100K / 128 | Owner＋树 | 2.042 | 3.625 | 9.167 |
| 100K / 128 | Owner＋树＋扫描 | 2.750 | 9.750 | 38.459 |

原始 JSON 还记录每轮 maxNs、完成扫描数和 opsPerSecondIncludingDrain。
该吞吐值包括前台停止后等待最后一次扫描排空的时间；单操作延迟不包括排空。
极值受 GC/JIT/调度影响显著，部分达到毫秒级，不能凭三轮短测认定差异稳定。

本次数据支持的结论：排序树存在时，正常更新的中位数差距比裸字典实验小；
持续后台扫描仍会增加尾延迟，尤其 100K 组的 p99.9。不能据此宣称锁等待已消除，
也不能把一两组更低分位数解释成优化加速。

## 决策依据与尚缺证据

共享成员字节可避免长度相关副本，但仍有约 72 字节/成员的稳定节点增量，
百万成员量级约为 68.7 MiB，属于按测得增量外推，未在本轮测量百万成员。
是否值得接受，需要与目标数据集、旧值保护收益共同判断。
在接入前应先明确字典值直接使用节点、已有数组可安全共享的路径，并设计同锁范围内
更新树与 Owner 的接口，避免当前适配器重复获取 gate。
本轮尚未测多前台线程的性能、插入/删除性能、不同覆盖率、编码输出和真实 CPR；
并发压力测试的操作计数不是这些性能结果的替代。
