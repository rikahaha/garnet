## 结论 1：Owner 每次插入多分配约 72 字节，符合预期

每次操作的分配量（删除和插入各算一次）：baseline 48 / 104 字节（16 / 128 字节成员），owner 84 / 140 字节，多 36 字节/操作，
即每次插入多一个约 72 字节的节点对象。

## 结论 2：workstation GC 下，Owner 让 GC 总停顿增加约 30–85%，最长停顿增加 0–56%

3 次运行中位数：

| 规模 / 长度 | GC 次数（gen0/1/2）baseline → owner | 总停顿 ms baseline → owner | 最长停顿 ms baseline → owner |
| --- | --- | --- | --- |
| 10K / 16 | 2/0/0 → 3/1/0 | 39.8 → 68.9（+73%） | 19.9 → 31.2（+56%） |
| 10K / 128 | 5/3/1 → 6/3/1 | 68.8 → 89.4（+30%） | 22.1 → 22.5（约相同） |
| 100K / 16 | 3/2/1 → 4/3/1 | 132.6 → 236.5（+78%） | 73.7 → 87.9（+19%） |
| 100K / 128 | 5/4/1 → 6/5/1 | 159.9 → 296.0（+85%） | 60.3 → 86.1（+43%） |

- 这个负载下，**baseline 自己就有 20–74 ms 的 GC 停顿**，各组的最大延迟几乎都等于最长 GC 停顿。
  也就是说，在 workstation GC、持续分配的情况下，尾延迟首先由 GC 决定；Owner 让它更严重。
- 只有 3 次运行，停顿时长的波动没有评估；百分比只能看量级。

## 结论 3：server GC（8 个堆）在 100 万次操作内一次 GC 都没有发生，GC 成本无法评估

- 所有 server GC 运行的测量期间 GC 次数为 0，峰值工作集 120–267 MB。这一部分**没有回答** "Owner 是否让 server GC 更重"。
  Garnet 实际使用 server GC，所以这一项仍是空白，需要更长的运行或更大的分配量。
- 不涉及 GC 时的正常更新延迟（中位数）：owner 相对 baseline，p50 多 0.1–0.2 μs，p99 多 0.3–1.3 μs（100K/16：1.30 → 2.56 μs）。

## 结论 4：持续增删时，单次扫描可能造成毫秒级停顿，原因未明

| GC | 规模 / 长度 | 扫描耗时 | 最大延迟（3 次） | ≥1 ms 的操作（与 GC 停顿重叠） |
| --- | --- | --- | --- | --- |
| server | 100K / 16 | 8.4–9.3 ms | 1.4、1.9、1.6 ms | 每次 1 个（0 个重叠） |
| server | 100K / 128 | 9.8–10.1 ms | 3.8、3.6、3.9 ms | 每次 1 个（0 个重叠） |
| server | 10K | 1.9–2.3 ms | 137–162 μs | 0 |
| workstation | 100K / 128 | 94–96 ms | 84–86 ms（GC） | 6、8、10 个（4、3、5 个重叠） |

- server GC、10 万成员时，每次运行都有 1 个 1.4–3.9 ms 的操作，**不与任何 GC 停顿重叠**，时长短于扫描本身（8–10 ms）。
  候选原因：扫描线程在批与批之间很快重新拿到 gate，前台线程等不到锁（锁不公平）；或者操作系统调度。
  本次没有记录慢操作是否落在扫描区间内，也没有记录每次操作的 gate 等待时间，**不能确认**。
- workstation GC、100K/128 时扫描被拉长到约 95 ms（server GC 下约 10 ms），期间有一半左右的慢操作不与 GC 停顿重叠。
- 这和此前笔记本上 "单次扫描只带来几十微秒干扰" 的短测结果不同：那次没有持续分配，也不是这台机器。
