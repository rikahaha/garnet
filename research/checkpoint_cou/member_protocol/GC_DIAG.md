# GC 与慢操作诊断、单次扫描干扰（第二版）

2026-10-30，本机 Darwin arm64，.NET 10.0.403，Release，workstation GC（`server: false`，并发 GC 开启）。
只修改 member_protocol：`GcDiag.cs`、`run_gc_diag.py`、`Program.cs` 的 `--gc-diag` 入口、`CostStudy.Keys` 改为 internal。
未接入 Garnet、未连接服务器、未提交。

第一版（`results/gc_diag.jsonl`）的方法有四处问题，已在本版修正，第一版结论作废：

1. GC 证据只有"操作前后 GC 计数变化"，不能说明 GC 停顿落在该操作内；
2. 扫描窗口只收"扫描开始后才启动"的操作，会漏掉扫描开始前启动、随后等待 gate 的操作；
3. 对照窗口固定 5,000 次操作，扫描窗口只有几百次，最大值不可比；
4. 没有显式设置分层编译和 GC 相关环境变量；并且错误地假设"未 settle 时结构仍在第 0 代"。

## 方法

沿用 `CostStudy.TreeStore`（字典＋排序树；Owner 版本用 Owner 取代分数字典）、相同的成员生成和固定互质步长。
暖身 20K 次后测 100K 次更新。三种变体：

- `baseline`：字典＋排序树
- `owner`：Owner＋排序树，无扫描
- `scan1`：Owner＋排序树，第 25,000 次操作时后台启动**一次**完整扫描（128 节点/批，批间 Yield）

每次操作记录两种 GC 证据：

- **计数变化**：操作前后读各代 `GC.CollectionCount`。读取区间比计时区间略宽，只表示"操作附近有一次 GC 完成"。
- **停顿重叠**：进程内 `EventListener` 订阅运行时 GC 事件，把 `GCSuspendEEBegin`→`GCRestartEEEnd` 作为停顿区间，
  与该操作的计时区间求重叠时长。这是本版用于归因的证据。

窗口：`scan1` 取**计时区间与扫描区间重叠**的操作（操作开始 ≤ 扫描结束，且操作结束 ≥ 扫描开始）。
`baseline`/`owner` 从第 25,000 次起取**与同配置 scan1 窗口相同数量**的操作（驱动先跑 scan1 再传入数量）。

条件（驱动删除继承的 `DOTNET_*`/`COMPlus_*`，再显式设置；均 `DOTNET_gcServer=0`）：

| 条件 | GCDIAG_SETTLE | DOTNET_TieredCompilation |
| --- | --- | --- |
| settle（建表和暖身后先做两次阻塞完整 GC） | 1 | 1 |
| nosettle | 0 | 1 |
| settle-notiered | 1 | 0 |

每种条件 2 规模（10K/100K）× 2 成员长度（16/128 B）× 3 变体 × 3 个独立进程，共 108 条：`results/gc_diag_v2.jsonl`。
复现：`python3 research/checkpoint_cou/member_protocol/run_gc_diag.py /usr/local/share/dotnet/dotnet <新文件名>`

另记录建表、暖身、测量各阶段的 GC 次数。36 次运行合计，**建表阶段已发生 gen0 约 62、gen1 约 40、gen2 约 26 次**，
所以 nosettle 时结构的大部分很可能已经不在第 0 代；第一版"结构仍在第 0 代"的假设不成立。

## 结论 1：大部分毫秒级慢操作与 GC 停顿直接重叠；GC 不是唯一来源

36 次运行合计，≥1 ms 的操作：

| 条件 | ≥1 ms 操作 | 与 GC 停顿重叠 | 其中停顿 ≥ 该操作延迟一半 | 测量期间 GC 停顿事件 |
| --- | --- | --- | --- | --- |
| nosettle | 36 | 32 | 32 | 32 |
| settle | 1 | 0 | 0 | 0 |
| settle-notiered | 8 | 0 | 0 | 0 |

- nosettle 下 36 次慢操作中有 32 次与 GC 停顿重叠，且停顿占了延迟的一半以上。测量期间共 32 次停顿事件，
  **每一次停顿都对应一次慢操作**。这是"这些慢操作由 GC 停顿造成"的直接证据。
- nosettle 下 baseline 也有 1.3–3.0 ms 的最大延迟（同样来自 GC），owner 的最大值并不系统性高于 baseline
  （例如 100K/16：owner 266–288 μs，baseline 2,651–3,044 μs）。最大延迟主要取决于 GC 何时发生，
  所以**不能**据此判断 Owner 是否增加了 GC 停顿；本实验也**不能**反推 COST_STUDY 中每个尖峰的原因。
- 有 13 次 ≥1 ms 的慢操作没有任何 GC 停顿重叠，原因未明。它们集中在少数几次运行内的相邻位置：
  例如 settle-notiered 10K/16 owner 第 1 次运行中，第 30,522–31,553 次操作之间有 5 次 1.3–1.8 ms；
  nosettle 10K/128 owner 第 2 次运行中，第 79,560–82,661 次之间有 3 次。成簇出现更像是一段时间内的外部干扰
  （操作系统调度、其他进程等），但本实验没有记录这类信息，不能确认。
- settle 后测量期间没有发生任何 GC，因此本实验**没有**测到"持续分配、GC 不断发生时，Owner 多出的对象是否让每次 GC 更慢"。

## 结论 2：本次先做完整 GC 的短测中，单次扫描的干扰在几十微秒级；扫描本身的分配可能触发 GC

以下"settle"结果来自每次 100K 操作的短测，测量期间没有发生 GC，不能代表长期运行的情况。
窗口操作数相同让最大值的比较更公平，但仍不能排除调度、GC 时机等因素造成的差异。

窗口统计（3 次运行中位数；max 为 3 次各自的值），单位 μs，同配置各变体窗口操作数相同：

| 条件 | 规模 / 长度 | 扫描耗时 | 窗口 n | owner 无扫描 p99 / max | scan1 p99 | scan1 p99.9 | scan1 max |
| --- | --- | --- | --- | --- | --- | --- | --- |
| settle | 10K / 16 | 0.67 ms | 359 | 1.4 / 1–8 | 7.9 | 70.2 | 66, 70, 76 |
| settle | 10K / 128 | 0.68 ms | 344 | 1.4 / 3–7 | 9.2 | 70.2 | 70, 75, 59 |
| settle | 100K / 16 | 2.39 ms | 614 | 2.5 / 3–12 | 11.2 | 79.1 | 71, 84, 79 |
| settle | 100K / 128 | 3.98 ms | 593 | 3.7 / 3–38 | 23.3 | 82.7 | 83, 70, 87 |
| settle-notiered | 100K / 16 | 2.59 ms | 2,221 | 1.1 / 1–8 | 4.8 | 8.4 | 60, 57, 53 |
| settle-notiered | 100K / 128 | 3.21 ms | 1,905 | 1.2 / 5–38 | 7.6 | 16.5 | 53, 60, 61 |
| nosettle | 100K / 128 | 9.02 ms | 602 | 3.1 / 6–8 | 26.4 | 5,179 | 108, 5,212, 5,179 |

- 本次 settle 短测中，扫描期间前台的 p99 升到无扫描时的数倍，最大值 45–87 μs，没有观察到毫秒级停顿。
- nosettle 100K/128 的 3 次运行中有 2 次在扫描期间出现约 5.2 ms 的停顿，且与 GC 停顿重叠：
  扫描每批分配一个新的 `List<Row>`，这些分配可能在扫描期间触发 GC。复用批缓冲可以减少这种情况，尚未验证。
- 窗口操作数只有几百到两千，p99.9 接近窗口最大值，只能看量级。

**限制**：这是独立原型的适配器，扫描只读取成员，不含编码、输出和写盘；批间 `Thread.Yield` 也影响结果。
不能据此推断接入 Garnet 后的干扰，也不能直接与 Garnet 中整对象序列化的停顿做定量比较。

## 结论 3：关闭分层编译后延迟明显下降，原因未确认

settle-notiered 相对 settle，所有变体的 p99 降到约四分之一到一半（例如 10K/16 baseline：1.6 → 0.4 μs）。
可能原因之一是暖身较短、测量时部分方法尚未完成优化编译，但本实验没有记录编译事件，不能确认，
也不能保证各变体受到同样程度的影响。因此：

- COST_STUDY 与本文 tiered 条件下的绝对 ns/μs 数字不宜直接引用；
- tiered 条件下变体之间的差异也要谨慎解读。

settle-notiered 下 owner 相对 baseline 的整体 p99：10K 两组均为 0.4–0.5 vs 0.4 μs；100K/16 为 1.2 vs 0.8 μs；100K/128 为 1.3 vs 1.1 μs。

## 尚未回答的问题

1. 持续分配（成员不断插入/删除）、GC 持续发生时，Owner 多出的对象是否增加 GC 次数或停顿时长；
2. 13 次不与 GC 重叠的成簇慢操作的来源；
3. 扫描分配触发 GC 的程度，以及复用批缓冲能否消除；
4. 分层编译对各变体影响是否相同（需要记录 JIT 事件或改为按时间暖身）。
