# 第三轮（cygnus）：写入优先、批缓冲复用、数组布局

2026-11-06 12:35–12:55 JST，cygnus，程序为本地 `2add8fa` 发布的 linux-x64 版本。CPU 范围与前两轮相同
（`numactl --physcpubind=1,3,5,7,9,11,13,15 --membind=1`，server GC 堆数 8），开始前目标 CPU 忙碌 0–1%。
原始数据：`results/round3_*.jsonl`（72 条）。运行后已删除服务器上的 `~/member-protocol/`。

## C：扫描期间的卡顿（10 万成员，扫描代码已预热，各 3 次）

扫描期间前台最慢一次操作（μs），三个数字是三次运行：

| GC | 长度 | 都不开 | 只开写入优先 | 写入优先 + 批缓冲复用 |
| --- | --- | --- | --- | --- |
| server | 16 | 1,829、1,928、1,455 | 74、52、44 | 51、50、44 |
| server | 128 | 5,269、2,222、4,218 | 54、58、52 | 54、53、53 |
| workstation | 16 | 64、94、66 | 49、44、48 | 50、66、51 |
| workstation | 128 | 29,627、1,539、2,493 | 49、**73,580、73,378** | 56、50、53 |

- **写入优先消除了锁不公平造成的毫秒级等锁**：server GC 下扫描期间最大延迟从 1.5–5.3 ms 降到 44–74 μs；
  这些操作的时间几乎全是等锁时间，开启后等锁最长 42–72 μs。
- **workstation/128B 只开写入优先时仍有 73 ms 卡顿**（3 次中 2 次）：这几次扫描期间发生了 GC（3 次运行共 3 次停顿），
  这是 GC 停顿，不是锁的问题。**加上批缓冲复用后，3 次运行的扫描期间都没有发生 GC**，最大延迟 50–56 μs。
  这和"扫描每批新分配列表会在扫描期间触发 GC"的推断一致；只有 3 次运行，且 GC 时机本身有随机性，仍需更多运行确认。
- 扫描耗时：server GC 下约 8–12 ms，开写入优先后略长（扫描让路）；workstation/128B 只开写入优先时 86 ms 是被 GC 拉长。
- 扫描期间 p99 在 27–75 μs，三种配置之间没有一致的高低。

## D：server GC、1,000 万次操作，baseline / 对象版 / 数组版

3 次运行中位数；最长停顿列出 3 次各自的值（ms）：

| 规模 / 长度 | 每次操作分配 B：baseline / 对象 / 数组 | 总停顿 ms：baseline / 对象 / 数组 | 最长停顿 ms：baseline / 对象 / 数组 |
| --- | --- | --- | --- |
| 10K / 16 | 48 / 84 / **48** | 35 / 31 / 44 | 33、34、130 / 28、27、115 / 33、105、43 |
| 10K / 128 | 104 / 140 / **104** | 24 / 28 / 26 | 21、21、41 / 20、19、136 / 21、22、21 |
| 100K / 16 | 48 / 84 / **48** | 50 / 49 / 51 | 46、76、46 / 45、136、46 / 45、47、77 |
| 100K / 128 | 104 / 140 / **104** | 50 / **122** / 69 | 32、49、32 / **78、168、79** / 35、42、35 |

- 数组版每次操作分配与 baseline **完全相同**，不再为每个插入的成员多分配一个对象；
- 上一轮发现的问题组（100K/128B）：对象版最长停顿 78–168 ms，**数组版 35–42 ms，回到 baseline 水平（32–49 ms）**；
  总停顿 69 ms，介于 baseline（50）和对象版（122）之间；
- 各组都偶有单次 100 ms 以上的停顿（baseline 也有），只有 3 次运行，单个离群值不作结论；
- 正常更新 p99：baseline 0.69–1.46 μs，数组版 1.09–2.04 μs，与对象版相近。数组布局降低的是 GC 成本，不是每次更新的锁和查找成本。

## 结论

1. 写入优先 + 启动预热：消除了扫描期间的毫秒级等锁卡顿（本次 server GC 下最大 ≤ 74 μs）；
2. 批缓冲复用：在 workstation/128B 下避免了扫描期间触发 GC（样本少，需确认）；
3. 数组布局：每个成员不再多一个对象，大集合的 GC 最长停顿回到 baseline 水平；
4. 仍存在：正常更新的 p99 比 baseline 高约 0.4–0.8 μs（锁和额外查找），这是正常运行的固有开销。

阶段 1 的目标（扫描期间无毫秒级卡顿、server GC 下额外成本可接受）在本次测量中基本达到。
