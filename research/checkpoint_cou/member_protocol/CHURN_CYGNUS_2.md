# 持续增删负载（第二轮）：扫描卡顿归因与 server GC 成本

2026-11-06 11:55–12:10 JST，cygnus，程序为本地 `2514895` 发布的 linux-x64 自带运行时版本。
CPU 范围 `numactl --physcpubind=1,3,5,7,9,11,13,15 --membind=1`；server GC 堆数 8。开始前这 8 个 CPU 忙碌 0–2%。
原始数据：`results/churn_jit_cygnus.jsonl`（A，24 条）、`results/churn_servergc_cygnus.jsonl`（B，24 条）。
运行后已删除服务器上的 `~/member-protocol/`。

## A：扫描卡顿的两个来源

10 万成员，`scan1`（扫描代码首次运行）与 `scan1warm`（扫描代码已在别的小集合上运行过一次），各 3 次：

| GC | 长度 | 变体 | 扫描单批最长占锁 μs | 最长那批是第几批 | 扫描期间最慢的前台操作 μs |
| --- | --- | --- | --- | --- | --- |
| server | 16 | scan1 | 405、377、375 | 1、1、1 | 1,505、1,785、1,675 |
| server | 16 | scan1warm | 20、22、19 | 117、94、5 | 1,564、1,726、2,041 |
| server | 128 | scan1 | 382、380、378 | 1、1、1 | 2,416、4,133、4,196 |
| server | 128 | scan1warm | 31、25、26 | 61、135、79 | 3,871、4,306、4,258 |
| workstation | 16 | scan1 | 359、364、411 | 1、1、1 | 389、397、425 |
| workstation | 16 | scan1warm | 16、17、16 | 280、254、225 | 68、75、74 |

**来源 1：首批的 JIT 编译。**扫描代码首次运行时，第 1 批持锁约 360–410 μs；预先运行过一次后降到 16–31 μs。
workstation/16B 下，这正是扫描期间最大延迟的来源（约 400 → 约 70 μs）。

**来源 2：锁不公平（新确认）。**server GC 下（以及 workstation/128B 的大部分运行），预热后单批最长只占锁 20–31 μs，
但扫描期间仍有一个前台操作慢 1.5–4.3 ms，而且：
- 这 1.5–4.3 ms **几乎全部是等锁时间**（gateWait 与延迟相差 < 5 μs）；
- 与 GC 停顿**没有重叠**（server GC 的扫描期间没有发生任何 GC）；
- 每次运行 1 个，长度约为扫描总时长（7–10 ms）的 20–45%。

一个前台操作等锁的时间远大于任何一批的占锁时间，说明扫描线程在两批之间又抢回了锁，前台线程连续多批都没拿到。
`lock`（Monitor）不保证公平，被阻塞而进入睡眠的线程被唤醒前，正在运行的线程可以反复重新获取。
这是根据计时推断的机制，没有直接追踪锁的获取顺序。

唯一一次更长的扫描期卡顿（workstation/128B scan1 第 3 次，73 ms）完全是 GC 停顿，与锁无关。

**修法方向**：两者都需要。预热（启动时运行一次扫描代码）消除来源 1；来源 2 需要写入优先，
例如前台等锁时登记，扫描线程每批结束后若有人在等，就不立刻重新获取，而是等到对方拿到并释放锁。

## B：server GC 下 Owner 的 GC 成本（1,000 万次操作）

这次测量期间 server GC 确实发生了（每次运行 4–6 次 GC，其中 1 次 gen2）。3 次运行中位数：

| 规模 / 长度 | GC 次数 g0/g1/g2：baseline → owner | 总停顿 ms：baseline → owner | 最长停顿 ms（3 次）：baseline → owner |
| --- | --- | --- | --- |
| 10K / 16 | 2/1/1 → 3/2/1 | 34.6 → 31.5 | 33、33、34 → 28、28、28 |
| 10K / 128 | 3/2/1 → 4/3/1 | 23.9 → 26.2 | 21、21、21 → 20、19、19 |
| 100K / 16 | 2/1/1 → 2/1/1 | 49.2 → 48.5 | 45、45、46 → 46、46、45 |
| 100K / 128 | 3/2/1 → 3/1/1 | 51.1 → **124.3** | 32、46、32 → **78、183、79** |

- 4 组中 3 组，Owner 的 GC 总停顿和最长停顿与 baseline 相当；
- **100K/128B 组明显变重**：最长停顿约 2.5–4 倍（78–183 ms），每次运行都如此。这一组存活对象最多（成员 + 节点），
  候选解释是 gen2 回收时要标记的对象更多，但本实验没有分解停顿内部的阶段，不能确认；
- 每次运行只有 4–6 次 GC，最长停顿基本由那 1 次 gen2 决定，样本很少；
- 正常更新的 p99：baseline 0.69–1.42 μs，owner 1.04–1.95 μs。

## 结论与下一步

1. 扫描卡顿的原因已基本查清（JIT + 锁不公平），可以在原型里修复并复测（阶段 1.2）；
2. server GC 下，大集合（100K/128B）的 gen2 停顿明显变长，**每成员一个节点对象的代价是实际存在的**，
   分段数组方案（阶段 1.5）应当做；其余三组没有观察到差异；
3. 批缓冲复用（阶段 1.4）仍按约定单独测。
