# cygnus：参照 Garnet 论文第 8 节设计的实验（2026-11-28）

GarnetServer `ckpt-delta` 的 `75deedd`（Garnet 代码与之后的提交相同），`paper_eval.py`（`672024c`），`run_paper_server.sh`。
server `numactl --cpunodebind=1 --membind=1`，客户端 `--cpunodebind=0 --membind=0`；开始前负载 0.64。`-m 32g`，缓存模式（无
`--storage-tier`）。每组 2 次重复。所有大集合运行结束时 ZCARD 都等于预装成员数（`*_sizes.txt`，无 WARNING）。服务器目录已删除。

配置：`baseline`（全关）、`viewpooled`（成员视图 + 池化缓冲）、`delta`（再加成员级增量，阈值 1 万成员）。
逐次汇总：`summary_tables.txt`（由 `run_paper.log` 生成）、`rounds.csv`、`savetime.csv`、`zaddrem.csv`。

## 1. 小集合对照（论文图 7a 设置）

Resp.bench `--op ZADDREM --dbsize 1024 -b 1024`，10 s/格。每批加入再删除相同成员，集合几乎为空。有 checkpoint 时每 2 s 一次 BGSAVE
（运行期间 23 次）。单位 M ops/s，两次平均：

| 线程 | baseline | baseline + ckpt | delta | delta + ckpt | delta / baseline（无 ckpt） |
| --- | --- | --- | --- | --- | --- |
| 1 | 1.19 | 1.08 | 1.01 | 0.94 | −15% |
| 4 | 3.99 | 3.79 | 3.37 | 3.28 | −16% |
| 16 | 12.86 | 12.41 | 11.80 | 11.46 | −8% |
| 64 | 24.20 | 23.34 | 24.42 | 22.81 | +1% |

**开销来自成员存储本身**（不做 checkpoint 也慢）：成员模式下所有 SortedSet（包括只有几个成员的）都用分段数组 + 写锁。
修法：小集合继续用字典，超过阈值再转换。

## 2. 无负载 SAVE 耗时（论文 8.6 节方式）

20 × 100 万成员，先 SAVE 一次，再对每个集合改 1% 的成员（ZINCRBY），再 SAVE。checkpoint 时长（ms）：

| | 第 1 次（全量） | 第 2 次（改 1% 后） | 第 2 次写出 |
| --- | --- | --- | --- |
| baseline | 1221、1220 | 932、933 | 全部（约 380 MB） |
| viewpooled | 1318、1464 | 977、982 | 全部 |
| delta | 2171、2383 | **374、372** | 差量 4.0 MB（完整 398 MB） |

## 3. 连续 6 次 checkpoint（16 个连接，第 5、12、…、40 s BGSAVE）

每次：时长 / checkpoint 期间吞吐量占平时 / 最大延迟。两次重复的范围：

| | 第 1 次 | 第 2–5 次 | 第 6 次 |
| --- | --- | --- | --- |
| baseline，均匀 | 0.6–0.8 s / 47–48% / 133–282 ms | 0.44–1.15 s / 24–60% / 89–763 ms | 0.45–1.1 s / 30–55% / 97–678 ms |
| viewpooled，均匀 | 1.9–2.0 s / 93–94% / 94–128 ms | 0.97–1.11 s / 99–103% / 0–6 ms | 0.99–1.03 s / 100–102% / 0 ms |
| **delta，均匀** | 2.4 s / 99–101% / 4–5 ms | **0.55–0.59 s / 97–102% / 0–1 ms** | 2.0–2.1 s（链满 4 个差量，重写完整）/ 95–99% / 1–119 ms |
| baseline，Zipf | 0.67–0.73 s / 40–47% / 163–172 ms | 0.40–1.12 s / 24–65% / 71–770 ms | 0.40–0.45 s / 63–65% / 75–77 ms |
| viewpooled，Zipf | 1.6–1.8 s / 84–101% / 4–297 ms | 0.96–1.04 s / 99–103% / 0–1 ms | 0.98–1.21 s / 89–101% / 0–168 ms |
| **delta，Zipf** | 2.4 s / 101–102% / 4–5 ms | **0.47–0.58 s / 87–104% / 0–102 ms** | 2.0 s（重写完整）/ 101% / 0–1 ms |

每次 checkpoint 写出（`rounds.csv`）：viewpooled 每次 378 MB；delta 第 2–5 次均匀 27–30 MB（两次之间改动 6.8–7.5% 的成员）、
Zipf 16–17 MB（4.1–4.3%）。

**结论**（可用于论文的写法）：在 16 个连接持续访问 20 个百万成员 SortedSet 的实验中，首次全量 checkpoint 后，连续四次差量
checkpoint（第 2–5 次）均在 0.47–0.59 s 内完成；相较 viewpooled 每轮写出约 378 MB，每轮差量写出 16–30 MB（减少约 92–96%），
期间吞吐量接近平时水平。第 6 次因链长上限（4 个差量）重写全量，耗时约 2 s。这个周期（平常轮次的收益 + 定期重写的成本）应在论文中展示。

视图和增量各自的贡献：第 2–5 次中，viewpooled 已把最大延迟控制在 6 ms 以内，增量进一步把 checkpoint 从约 1 s 缩到约 0.5 s。
增量有一轮出现 102 ms 的最大延迟，所以"吞吐量接近平时"成立时，个别请求仍可能明显变慢。

适用边界：只改 1% 后无负载 SAVE，增量写 4 MB、0.37 s（baseline 0.93 s）；而高负载下均匀更新覆盖 20–25% 的成员时，增量第 2 次
1.1–1.9 s，长于 baseline 的 0.6–0.75 s（第 4 节）。改动比例与并发压力各贡献多少成本，需要分段计时确认。

## 4. 扩展连接数（16 / 64 / 128）

20 s，第 5、12 s BGSAVE，只有 2 次 checkpoint。完整表见 `summary_tables.txt`。要点：

- 服务器在 64–128 个连接时基本饱和：平时吞吐量 1.1–1.7 M ops/s，三种配置之间看不出系统性差别（单次噪声约 ±10%）。
- checkpoint 期间吞吐量占平时：baseline 29–60%（最大延迟 165–1075 ms）；viewpooled 76–114%；delta 62–113%。
  viewpooled / delta 在 64–128 个连接时仍偶有 150–660 ms 的最大延迟（16 个连接时基本 ≤ 10 ms）。
- **高负载下增量的第 2 次 checkpoint 变长**：均匀负载 64 / 128 个连接时 1.1–1.9 s，长于 baseline（0.58–0.75 s）。
  原因：两次 checkpoint 之间改动的成员达到 20.7% / 24.5%（接近 25% 上限），差量 82–97 MB；且为找出改动成员，仍要扫描每个集合的
  全部成员（O(集合大小)），这次扫描与前台请求争 CPU。Zipf 负载下改动较少（约 12%），delta 第 2 次 0.9–1.0 s，短于 viewpooled（1.5 s）。
- delta 的第 1 次 checkpoint 在高负载下 3.0–3.4 s。

## 平时开销能说到什么程度

大集合在 64–128 个连接下看不出系统性的平时吞吐量差异；小集合（第 1 节）在 1–16 个连接下测到 8–16% 的退化。两者同时成立，
"平时开销很小"只适用于大集合，小集合的开销要在论文中明确报告（或用阈值消除后报告）。

## 待改进（由本次实验得出）

1. 小集合不使用成员存储（阈值 + 转换），消除 8–16% 的开销。
2. 维护"改动成员列表"，差量 checkpoint 不再扫描全部成员，使耗时与改动量成正比。
3. 高负载下仍有的 150–660 ms 停顿：记录 GC 事件确认来源。
4. 恢复速度（见 `../results_cygnus/RESULTS.md`：7.4 s vs 11.3–11.8 s）。
