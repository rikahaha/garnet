# 成员级增量 checkpoint：第 1 步，差量大小估计（本地）

2026-11-27，Apple M4 笔记本，分支 `ckpt-delta`。`delta_estimate.py`，10 个 SortedSet × 10 万成员（成员名如 `m12345`，每个成员写出约 18 字节）。

**只估计，不改写入**：快照照常完整写出。开关 `GARNET_DELTA_TRACE=<csv>` 打开时，每个集合写快照视图时额外记录：
完整写出多少字节，以及"相对上一次 checkpoint 只写新增/改过的成员 + 被删成员的 key"要多少字节。
估计假设上一次 checkpoint 已经完成（真正实现时，base 只在 checkpoint 完成后才前进）。

## 做法

- 成员存储里每个成员记一个修改 epoch（每打开一个视图，epoch 加 1）。视图记录读到的成员时，用"视图边界时那个值"的 epoch
  （成员在视图打开后又被改过，就用改之前保存的 epoch），所以 checkpoint 期间的写入算到下一次差量里。
- 删除：被删成员在上一个视图边界时已经存在，就按 epoch 计数。
- 两次 checkpoint 之间按负载修改，checkpoint 时没有写入；脚本知道每个集合改了哪些成员，和服务器的计数逐个比对。

## 结果（10 个集合合计）

| 两次 checkpoint 之间的负载（每个集合） | 完整写出 | 差量 | 差量 / 完整 | 计数核对 |
| --- | --- | --- | --- | --- |
| 均匀，改 0.1% 成员（+0.01% 删除和新增） | 17.9 MB | 0.021 MB | 0.12% | 一致 |
| 均匀，改 1% | 17.9 MB | 0.21 MB | 1.2% | 一致 |
| 均匀，改 10% | 17.9 MB | 2.1 MB | 11.6% | 一致 |
| 均匀，改 50% | 18.0 MB | 10.4 MB | 57.9% | 一致 |
| Zipf(1.0)，操作数 = 1% 成员数 | 18.0 MB | 0.11 MB | 0.62% | 一致 |
| Zipf(1.0)，操作数 = 10% | 18.0 MB | 0.77 MB | 4.3% | 一致 |
| Zipf(1.0)，操作数 = 100% | 18.0 MB | 4.4 MB | 24.4% | 一致 |

均匀负载下差量略大于修改比例，因为还包含删除和新增（各为修改数的 1/10）。Zipf 下热点成员被反复修改只算一次，
所以操作数等于成员数时，差量也只有完整写出的约 1/4。

## 其他检查

- 恢复正确性场景 C（成员模式，3 次 checkpoint 期间持续写入，kill -9 后恢复）：PASS。
- `Garnet.test.collections` 中的 SortedSet 测试（成员模式）：351 个全部通过。

## 结论和下一步

改动比例小或有热点时，差量只有完整写出的 0.1%–5%，值得做真正的差量写入（方案 B：快照里只存存根，成员数据由 Garnet 侧按集合保存
完整版本 + 差量链）。差量超过完整大小的约 25% 时直接写完整版本（均匀改 50% 的情况）。

尚未测：checkpoint 期间有写入时的估计（这时部分修改会算到下一次）；100 万成员规模（比例应与规模无关）。
